## 一、评测集设计

### 1.1 RAG 系统专项评测集

> 基于 15 份上市公司年报(5 家公司 × 3 年,18801 chunks)构建,这是 RAG 简历深度最关键的量化依据。

**评测集规模与分布(50-80 条)**:

| 类别 | 条数 | 覆盖场景 | 示例 |
|---|---|---|---|
| **单文档检索** | 20 | 同一公司年报内的事实查询 | "五粮液 2021 年营业收入是多少?" |
| **跨文档检索** | 15 | 多公司对比 / 同公司多年对比 | "对比贵州茅台和五粮液 2022 年的毛利率" |
| **段落召回 + fallback** | 10 | 小节超 2000 字触发 fallback | "海康威视 2023 年研发费用明细" |
| **多路召回命中** | 10 | BM25 强 / 向量强 / 双路命中的不同 case | "宁德时代电池产能"(向量强)/"六、主要会计数据"(BM25 强) |
| **拒答场景** | 5-10 | 知识库外问题应拒答 | "比亚迪 2024 年销量"(库内无此文档) |
| **引用溯源** | 10 | 答案引用来源是否准确(页码 + 章节) | 答案声称 p6 但实际在 p23 → 判错 |

**RAG 专项指标**:

| 指标 | 计算方式 | 目标 |
|---|---|---|
| **Recall@K** | Top-K 候选是否包含正确文档(K=5/20) | ≥ 90% |
| **MRR** | 正确文档排名倒数的平均 | ≥ 0.7 |
| **段落召回命中率** | 段落扩展后是否覆盖答案所在小节 | ≥ 95% |
| **fallback 触发准确率** | 超 2000 字 fallback 是否真的必要(非误触) | ≥ 80% |
| **引用准确率** | 答案引用的 doc_name + page_num + heading_path 是否正确 | ≥ 90% |
| **答案事实准确率** | LLM-as-Judge 判定答案数值/事实是否与原文一致 | ≥ 85% |
| **拒答率** | 知识库外问题正确拒答的比例 | ≥ 90% |
| **多路召回贡献度** | BM25-only / 向量-only / 融合 三种策略的 Recall 对比 | 融合 > 单路 ≥ 5% |

### 1.2 Agent 编排评测集

- 单工具场景:RAG / SQL / web_search 各 10 条
- 多工具编排场景:10 条(如 RAG + web_search 链式)
- 多轮对话场景:5 条

**Agent 专项指标**:
- 工具选择准确率 / 参数填充正确率 / 答案事实准确率(LLM-as-Judge)

## 四、混合融合策略 + cosine 拒答(2026-08-04)

> **问题**:基线评测发现 fused_candidates 的 top1_score 全是 0.700,根因是 min-max 归一化 + 加权融合导致单路命中的 chunk 分数被卡在固定值(仅 RAG 路=0.7,仅 BM25 路=0.3),直接后果是拒答阈值 0.3 形同虚设,refusal 类 5 条全部"拒答失败"(拒答率=0%)。

> **方案迭代**:先试纯 RRF(A 方案),Recall@5 提升 2.2% 但 Recall@20 下降 6.2%(cross_doc -11.9%),因 RRF 对单路命中 chunk 惩罚过大;最终采用混合策略(top-5 RRF 精排 + top-20 加权融合召回)+ D 方案(cosine 拒答),兼顾精度与召回。

### 4.1 混合策略实现

- [store.py](../doc-service/store.py) `hybrid_fuse` 同时计算 `weighted_score`(min-max 归一化 + 加权)和 `rrf_score`(RRF k=60)
- **算法**:1) 按 weighted_score 取 top-20(保证召回广度);2) 对 top-20 按 rrf_score 取前 5(精排,提升 Precision@5);3) 最终顺序 = [rrf top-5] + [剩余 15 个按 weighted 降序]
- `score` 字段统一用 weighted_score(量纲一致),追加 `rrf_score` 字段供调试
- 每条候选追加 `bm25_rank` / `rag_rank` / `bm25_raw_score` / `rag_raw_score`(各路原始分,供拒答判断用)

### 4.2 D 方案:cosine 拒答判断

- [main.py](../doc-service/main.py) `CandidateItem` 追加 `bm25_raw_score` / `rag_raw_score` 字段(非破坏性)
- Go 端 [client.go](../agent-go/internal/rag/client.go) `CandidateItem` 同步追加 `BM25RawScore` / `RAGRawScore`
- [rag_eval.py](../scripts/rag_eval.py) `refusal_check` 改用 `fused_candidates[0].rag_raw_score`(bge-large-zh raw cosine)判断拒答,阈值 0.86
- **阈值 0.86 依据**:实测 bge-large-zh 对中文年报 cosine 分布——refusal 类 0.83-0.91 vs 正常类 0.89-0.92,0.86 是分布自然 gap(refusal 最低 0.8329/0.8558 < 0.86 < 正常最低 0.8925,margin=0.0325)

### 4.3 三方案对比(64 case)

| 指标 | 加权融合(原基线) | 纯 RRF | **混合策略(最终)** | vs 原基线 |
|------|------------------|--------|---------------------|-----------|
| **拒答率** | 0.0% | 40.0% | **40.0%** | **+40%** |
| **Recall@5** | 85.9% | 88.1% | **88.4%** | **+2.5%** |
| **Recall@20** | 96.0% | 89.8% | **96.0%** | **持平** |
| **cross_doc R@20** | 90.5% | 78.6% | **90.5%** | **持平** |
| **通过率** | 28.1% | 20.3% | **31.2%** | **+3.1%** |
| 段落召回命中率 | 22.0% | 13.6% | 22.0% | 持平 |
| fallback 合理率 | 80.0% | 50.0% | 70.0% | -10% |
| MRR | 0.8 | 0.8 | 0.8 | 持平 |
| 平均耗时(ms) | 327.1 | 360.6 | 373.5 | +46.4 |

### 4.4 结论

- **混合策略全面优于原基线**:Recall@20/cross_doc/段落召回保持 96%/90.5%/22% 不退化,Recall@5 提升 2.5%,拒答率从 0% 提升到 40%,通过率从 28.1% 提升到 31.2%
- **核心设计**:top-5 RRF 精排利用排名共识提升 top 精度,top-20 加权融合保留单路命中 chunk 的召回广度,cosine 拒答独立于融合方式(用绝对相关度判断)
- **fallback 合理率 80%→70%**:轻微下降,因部分 case top-5 排序变化影响 section_recall 输入,属可接受范围
- **bge-large-zh 区分度不足**:refusal 和正常 case 的 cosine 重叠区 0.89-0.91,单一阈值无法完全区分。后续优化:1) 换用区分度更好的 embedding 模型;2) 加 rerank 模型做二次过滤;3) 结合 BM25 分数联合判断拒答

## 五、融合方案迭代工程踩坑总结(2026-08-04)

> 本节记录从「加权融合基线」→「纯 RRF」→「混合策略」三次迭代中踩到的工程坑,供后续调参/换模型/扩展检索路时参考,避免重复试错。

### 坑 1:min-max 归一化掩盖单路命中(原基线的根本 bug)

- **现象**:64 条 case 的 `fused_candidates[0].score` 全是 0.700,无任何区分度;拒答阈值 0.3 形同虚设,5 条 refusal case 全部"拒答失败"(拒答率=0%)。
- **根因**:`hybrid_fuse` 用 min-max 把每路最高分归一到 1.0,单路命中 chunk 的另一路补 0,融合分固定为权重乘积——仅 RAG 路命中永远 0.7,仅 BM25 路命中永远 0.3。归一化把"绝对相关度"信息全部抹掉,只剩"本路内相对排名"。
- **教训**:两路量纲不一致时不要直接 min-max 后加权;若必须加权,至少保留 raw score 副本供下游做绝对阈值判断。归一化是"内卷"——只在同路内有意义,跨路加权后分数失去绝对语义。
- **解法**:hybrid_fuse 同时保留 `bm25_raw_score` / `rag_raw_score`,拒答判断改用 raw cosine(D 方案),不再依赖融合分。

### 坑 2:纯 RRF 对单路命中 chunk 惩罚过大

- **现象**:换纯 RRF 后 Recall@5 提升 2.2%(精排变好),但 Recall@20 下降 6.2%,cross_doc 场景暴跌 11.9%。
- **根因**:RRF 公式 `1/(k+rank)`,单路命中 chunk 只有一路贡献,分数 ≈ `0.7 * 1/(60+1) ≈ 0.0115`;而加权融合单路命中 chunk 分数 ≈ 0.7。RRF 把单路命中 chunk 的绝对分压到极低,在 top-20 边界处被双路命中但相关度更低的 chunk 挤出。中文年报场景 BM25 偏弱(MySQL FULLTEXT ngram 对长尾业务术语召回不强),大量相关 chunk 仅向量路命中,成为 RRF 的牺牲品。
- **教训**:RRF 假设"两路都有合理召回",若某路召回偏弱,RRF 会系统性惩罚单路命中样本。换融合策略前必须先看各路独立 Recall,评估单路命中比例。
- **解法**:混合策略——top-20 仍用加权融合(保留单路命中召回广度),仅 top-5 用 RRF 精排(此时所有候选已在 top-20 内,单路惩罚只影响排序不影响召回)。

### 坑 3:bge-large-zh cosine 区分度不足,阈值难定

- **现象**:refusal case(如"比亚迪 2024 年销量")的 top1 rag_raw_score=0.83-0.91,正常 case 0.89-0.92,两者重叠区 0.89-0.91,单一阈值无法完全区分。
- **根因**:bge-large-zh 对中文长文本的 cosine 分布偏高且压缩,相关/不相关查询的分数区间重叠。模型本身设计目标是排序而非绝对相关度判断。
- **教训**:不要照搬论文里的 cosine 阈值(如 0.5),必须在自己的数据集上实测分布定阈值。定阈值的方法:取 refusal 类最低分和正常类最低分之间的 gap 中点,并留出 margin。
- **解法**:实测 9 条样本(refusal 5 + 正常 4),发现 gap 在 0.86,定为阈值。剩余 3 条 refusal 的 cosine > 0.89 落在重叠区,单一阈值无解,需 rerank 或换模型。

### 坑 4:阈值选择的方法论——不要拍脑袋

- **错误做法**:最初把 cosine 阈值设为 0.5(参考通用经验值),实测发现所有 refusal case 的 cosine 都 > 0.83,阈值完全无效。
- **正确做法**:批量跑 refusal + 正常 case 各 5 条,打印 top1 rag_raw_score,观察分布找到自然 gap(0.86),而非强行用 0.5 或 0.9。
- **教训**:阈值是数据分布的函数,不是超参。任何阈值都必须有实测分布依据,并在文档中记录依据(便于后续换数据集时重新校准)。

### 坑 5:接口字段非破坏性追加的工程纪律

- **现象**:首次改造时差点把 `CandidateItem.score` 的语义从"加权融合分"改成"RRF 分",会破坏所有下游评测脚本的阈值判断。
- **正确做法**:`score` 字段保持原语义(weighted_score),新字段(`rrf_score` / `bm25_raw_score` / `rag_raw_score` / `bm25_rank` / `rag_rank`)全部用 `Field(default=...)` 追加,旧消费者零感知。Go 端 `CandidateItem` 同步追加 `BM25RawScore` / `RAGRawScore`,JSON tag 对齐。
- **教训**:改接口时先问"这个字段有没有下游消费者"。`score` 这种通用字段改语义等于破坏性变更,即便没有版本号也要当 major breaking change 对待。新能力尽量加字段,不要改老字段语义。

### 坑 6:Python/Go 双端字段同步

- **现象**:Python 端 `CandidateItem` 加了 `rag_raw_score`,Go 端 `client.go` 的 `CandidateItem` 没同步,导致 Go 端反序列化时该字段被丢弃,评测脚本通过 agent-go 代理调用时拿不到 raw score。
- **正确做法**:Python 端字段变更后,立即同步 Go 端结构体(JSON tag 对齐),并在 PR 描述里列明双端字段清单。
- **教训**:跨语言项目任何 DTO 变更都是双端变更,只改一端等于没改。建议在代码注释里标注"与 doc-service CandidateItem 对齐",触发任一端变更时 grep 找到另一端同步。

### 坑 7:实验数据必须 before/after 全量对比,不要只看涨的指标

- **现象**:换纯 RRF 后只看 Recall@5 涨了 2.2% 就觉得成功,差点漏掉 Recall@20 暴跌 6.2%、cross_doc 暴跌 11.9%。
- **正确做法**:每次改融合逻辑后全量重跑 64 条 case,输出 before/after 对比表,覆盖所有指标(Recall@5/20、MRR、cross_doc、拒答率、通过率、段落召回、fallback 合理率、耗时)。
- **教训**:单一指标上涨不等于方案变好。融合策略是 trade-off 游戏,必须看全貌。特别警惕"精度涨召回跌"——Recall@5 涨可能是把 top-20 的相关 chunk 提前了,也可能是把 top-20 外的不相关 chunk 塞进 top-5,后者是假涨。

### 坑 8:混合策略的 score 字段语义要保持一致

- **现象**:混合策略 top-5 按 RRF 排序,但 `score` 字段若用 RRF 分,会导致 top-5 的 score 量纲(0.01 级)与 top-6-20(0.3-0.7 级)不一致,评测脚本的阈值判断会错乱。
- **正确做法**:`score` 统一用 weighted_score(量纲一致),RRF 仅作为内部排序依据,额外暴露 `rrf_score` 字段供调试。top-5 的排序依据是 rrf_score,但对外展示的 score 仍是 weighted。
- **教训**:对外字段的量纲一致性优先于内部排序逻辑。内部用什么排序是实现细节,对外 score 必须可比较、可阈值判断。


## 六、Rerank Before/After 评测(2026-08-05)

### 6.1 评测配置

- **Rerank 模型**: `bge-reranker-v2-m3`(CrossEncoder, FP16 GPU, max_length=512)
- **Before**: `RERANK_ENABLED=false`, `strategy=fused`(仅混合融合,无 rerank)
- **After**: `RERANK_ENABLED=true`, `strategy=fused_rerank`(混合融合 + rerank top-5)
- **评测集**: 64 条 case, 6 类场景(single_doc/cross_doc/section_fallback/multi_recall/refusal/citation)
- **完整报告**: `scripts/eval/rerank_comparison.md`

### 6.4 核心发现

**rerank 在当前配置下未带来指标提升,反而轻微下降。**

原因分析:
1. **chunk 截断**: rerank 模型 max_length=512,但 chunk_size=800,超出部分被截断丢失关键信息
2. **chunk 级 vs 文档级匹配**: rerank 评估 query-chunk 语义相似度,但评测以 doc_name 为粒度
3. **融合排序已足够好**: 混合策略(top-5 RRF + top-20 加权融合)MRR 已达 0.8
4. **multi_recall 受影响最大**: 短 query 场景 rerank 语义匹配不如 BM25 精确匹配

### 6.5 改进建议

1. 增大 max_length 到 1024,避免 chunk 截断
2. 混合排序策略: `final_score = 0.5 * fusion_score + 0.5 * rerank_score`
3. 仅对 top-10 rerank,减少噪声
4. 场景路由: multi_recall 等短 query 场景跳过 rerank

### 6.6 工程启示

- **rerank 不是银弹**: 在融合排序已足够好的场景下,rerank 可能引入噪声,必须 before/after 量化评测
- **截断是隐形杀手**: rerank 模型的 max_length 必须 ≥ chunk_size
- **评测驱动决策**: 64 条 6 类场景评测集定位到 multi_recall(R@5 60%→40%)和 single_doc(R@5 100%→95%)的退化
