## 一、阶段 D:记忆生命周期(衰减 → 分层 → 唤起 → 合并 → 冻结)

### 1.1 数据库变更(agent_memories 新增 5 字段)

| 字段 | 类型 | 语义 |
|---|---|---|
| `tier` | ENUM('hot','cold') DEFAULT 'hot' | 冷热分层:hot=在 Chroma 可检索 / cold=仅 MySQL 不在 Chroma |
| `effective_importance` | INT DEFAULT 0 | 衰减后的有效重要度(初始=importance, 随时间衰减) |
| `merged_from` | JSON | 合并来源:被合并的原记忆 ID 数组(仅 summary 合并记忆有值) |
| `merged_at` | DATETIME | 合并时间(被合并的原记忆标记, 代替 deleted_at 区分"合并删除") |
| `last_decayed_at` | DATETIME | 上次衰减计算时间 |

索引:`idx_tier_project (tier, project_id)` / `idx_effective_importance`。

### 1.2 记忆衰减(D-P0)

**规则**:
- 初始 `effective_importance = importance`(新建时)
- 命中时 `+5`(上限 100,bumpExistingMemory 同步更新)
- 衰减时每周 -3,30 天宽限,下限 10
- `source=manual` 豁免(手动记忆不衰减)
- 公式:`effective_importance = GREATEST(10, importance - FLOOR((DATEDIFF(now, last_accessed_at)-30)/7)*3)`

**双触发**:
- 懒计算(Python `store._apply_decay`):/search 融合后对结果计算,衰减严重的 score ×0.9
- 定时扫描(Go `decay.go` RunDecaySweep):每日 03:00,覆盖长期未被检索命中的记忆

### 1.3 冷热分层(D-P1)

**规则**:`effective_importance < 30` 或 `90 天未访问` → hot→cold。
**迁移**:查候选 → 调 Python /delete 移出 Chroma → UPDATE tier='cold'(Go `decay.go` runTierSweep, 每日 03:30)。
**注意**:BM25 内存索引**不区分 tier**,cold 记忆仍可被 BM25 搜到(这是唤起的前提)。

### 1.4 冷记忆唤起(D-P1)

**流程**:/search 中 BM25 命中 `tier=cold` 记忆 → 回填 Chroma + UPDATE tier='hot'。
- 单次最多回填 `COLD_RECALL_MAX=3` 条
- 响应新增 `cold_recall_count` / `cold_recall_ids` 字段
- 回填后 tier=hot,自然防抖;upsert 幂等防并发重复

### 1.5 记忆合并(D-P2)

**触发**:extractor 每 5 轮 LLM 深度提取后触发(`MaybeMerge`)。
**流程**:召回 fact 记忆 → 关键词重叠聚类(簇 ≥3 条)→ LLM 合并(最多 3 簇)→ 生成 summary(merged_from=原ID 数组, importance=max)→ 原 fact 标记 merged_at。
**成本控制**:复用用户自带 key / 系统 key,单次最多 3 次 LLM 调用;失败降级下轮重试。
**向量更新**:新 summary 标记 pending 待 embed,原 fact 调 /delete 移出 Chroma。

### 1.6 归档冻结(D-P3)

项目 `is_archived=true` 后:
- 衰减扫描 / 分层迁移 SQL 均 `JOIN agent_projects` 过滤 `is_archived=false`
- 合并 MaybeMerge 开头检查归档
- bumpExistingMemory(检索命中更新)检查归档,归档项目检索只读

## 二、阶段 C:性能与可观测性

### 2.1 检索缓存(C-P1, Redis 两级缓存)

| 级 | key | TTL | 失效 |
|---|---|---|---|
| L1 向量缓存 | `qv:{sha256(query)[:16]}` | 2h | 自然过期(query 向量与记忆变更无关) |
| L2 结果缓存 | `sr:{project_id}:{sha256(query)[:16]}:{top_k}` | 60s | upsert/delete/delete_collection 时按 project 清空 |

**降级**:Redis 不可用静默跳过;反序列化失败走正常路径;`CACHE_ENABLED=false` 完全绕过。
**实测**:L2 命中 16ms(vs 首次 755ms);缓存命中后评测 P50 5.9-20.6ms。
**踩坑**:本机老版 Redis(5.x)不支持 RESP3/HELLO,redis-py 8.x 默认协议连接失败 → cache.py 强制 `protocol=2` 兼容。

### 2.2 在线监控(C-P0)

- **内存环形缓冲**(metrics.py MetricsBuffer):保留最近 1000 次检索明细,同步写 ~0.01ms
- **MySQL 分钟聚合**(memory_search_metrics 表):异步线程写,同分钟 upsert 累加,不阻断响应
- **GET /metrics?project_id=&range=**:返回 realtime(P50/P95/P99 延迟 + 召回路数 + 缓存命中率 + 降权触发率)+ aggregated + capacity(hot/cold/merged 记忆数 + BM25 索引规模)
- **轻量告警**:P95>200ms 连续 10 次 / RAG 失败率>30% 写 WARN 日志

### 2.3 A/B 实验框架(C-P2)

- `scripts/eval/memory_ab_experiment.py --param BM25_WEIGHT --values 0.2,0.3,0.4`
- 参数覆盖:`X-AB-Override` header,仅 `AB_EXPERIMENT_MODE=true` 时生效(生产默认关闭)
- 可实验参数:BM25_WEIGHT / RAG_WEIGHT / RECALL_TOP_N / FINAL_TOP_K(白名单,防注入)
- 输出:`scripts/ab_reports/memory/{ts}_{param}/comparison.md`
