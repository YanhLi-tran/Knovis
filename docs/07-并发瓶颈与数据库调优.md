# 并发瓶颈与数据库调优

> 本文件归档:Knovis 单机部署的并发瓶颈分析、已发现的严重 bug、数据库连接池调优方案、万人并发生产级演进路径。
> 源自 2026-08-14 部署期间发现的"扫描文档时注册/登录失败"问题及其延伸分析。

---

## 一、已发现严重 Bug:扫描文档期间用户无法注册/登录

### 1.1 现象
- doc-service 执行 `/documents/scan` 批量导入 PDF 时,前端注册/登录请求返回 `400 Bad Request`
- 响应体:`{"code":400,"message":"context deadline exceeded"}`
- Knovis 用户服务日志显示 `POST /register` 耗时 3099ms 后返回 400

### 1.2 根因
1. **doc-service MySQL 连接池占用过多**
   - 配置:`mincached=2, maxcached=10, maxconnections=20`
   - 扫描时每篇年报 1000+ 分块,批量写入 `agent_document_chunks` 表持续占用连接
   - 同时 `upsert_vectors` 后还要查 chunks 元数据

2. **MySQL 服务器 `max_connections` 不足**
   - 默认值 151(MySQL 5.7/8.0 默认)
   - doc-service 占 20 + memory-service + agent-go + Knovis 用户服务,高峰期接近耗尽

3. **Knovis 用户服务连接超时**
   - go-zero 框架默认 MySQL 查询超时约 2 秒
   - 拿不到连接 → `context deadline exceeded` → 返回 400

### 1.3 影响
- 扫描期间(单篇 1-1.5 小时,15 篇约 18 小时)用户完全无法注册/登录
- 已登录用户不受影响(JWT 不查数据库)

### 1.4 待修复方案(P0)

#### 方案 A:限制 doc-service MySQL 连接数
- [x] `doc-service/store.py` 的 `_mysql_conn` 连接池 `maxconnections` 从 20 降到 8(2026-08-14 完成,提交 5d8092d;最终配置 mincached=2/maxcached=5/maxconnections=8)
- 扫描稍慢但用户服务永远能拿到连接
- 改动:1 行配置

#### 方案 B:提高 MySQL 服务器 max_connections
- [ ] MySQL 全局 `max_connections` 从 151 提到 200(服务器侧手工执行,不在代码库)
- 给各服务足够余量
- 改动:`SET GLOBAL max_connections=200;` + 修改 `my.cnf` 持久化

#### 组合效果
- doc-service 占 8 + 其他服务共享 192 连接 → 扫描期间用户注册/登录不受影响
- 扫描速度基本不变(瓶颈在 PDF 解析,不在 MySQL)

## 二、单机部署并发能力评估

### 2.1 当前架构(单机)

| 组件 | 配置 | 估算并发上限 |
|------|------|-------------|
| MySQL `max_connections` | 151 | ~100 并发查询 |
| doc-service 连接池 | 20 | 20 并发检索 |
| Knovis 用户服务 | go-zero 默认 | ~50 并发登录 |
| agent-go | 单进程 | ~100 并发对话 |
| Chroma 向量检索 | 内存暴力搜索 | ~50 并发检索 |
| PDF 解析 | 单线程,pymupdf4llm | 1 篇/1.5小时 |

### 2.2 实际可承载并发

- **稳定并发**:10-50 用户同时使用 ✅
- **峰值并发**:约 100 并发(超过后 MySQL 连接耗尽)⚠️
- **万人并发**:❌ 完全不可行

### 2.3 已知瓶颈点

1. **MySQL 连接池**:151 远不够万人并发(需 500+)
2. **Chroma 内存检索**:向量数量大时 OOM(评估时 18801×1024 float32 ≈ 75MB;2026-08-10 重摄 256/26 后实测 20833 条 ≈81MB——标题小节切分下分块数增长有限;10万向量 ≈ 400MB)
3. **agent-go 单进程**:单机单实例扛不住高并发
4. **PDF 同步解析**:用户上传后等 1+ 小时,阻塞请求
5. **BM25 内存索引**:全量 chunks 分词,内存占用随文档数线性增长

## 三、万人并发生产级演进路径

### 3.1 短期优化(支持 200-500 并发)

| 优化项 | 改动 | 预期效果 |
|--------|------|---------|
| MySQL `max_connections` → 500 | `my.cnf` + `SET GLOBAL` | 连接不再耗尽 |
| doc-service 连接池降到 8 | `store.py` 1 行 | 不抢占用户服务连接 |
| PDF 异步解析 | 引入 Celery/RQ 任务队列 | 用户上传后立即返回,后台解析 |
| agent-go 多副本 | docker-compose 启动 3 实例 + nginx 负载均衡 | 对话并发 ×3 |
| Chroma → Milvus 单机版 | 替换向量数据库 | 支持百万级向量 |

### 3.3 关键技术选型

| 组件 | 当前(单机) | 生产级 | 选型理由 |
|------|------------|--------|---------|
| MySQL | 单机 151 conn | 主从集群 500+ conn | 读写分离分担压力 |
| 向量库 | Chroma 单机内存 | Milvus 集群 | 支持十亿级向量,分布式检索 |
| PDF 解析 | 同步 pymupdf4llm | Kafka + Worker 池 | 异步处理,不阻塞用户 |
| agent-go | 单进程 | K8s 多副本 + HPA | 自动扩缩容 |
| Redis | 单机 | Redis Cluster | 高可用 + 分片 |
| 限流 | 无 | Sentinel/Kong 限流 | 保护后端不被打挂 |
| 监控 | tmux 看日志 | Prometheus + Grafana | 指标告警 |

### 3.4 演进路径(简历可写)

1. **当前(单机演示)**:支持 10-50 并发,适合秋招演示
2. **短期优化**:连接池调优 + 异步 PDF 解析 → 支持 200-500 并发
3. **生产级**:微服务多副本 + 向量数据库集群 + 消息队列 → 支持 1万+ 并发

## 五、面试话术参考

### Q: 你的系统能支持多少并发?
> 当前单机部署支持 10-50 并发稳定使用。主要瓶颈在 MySQL 连接数(151)和 Chroma 内存检索。短期优化(连接池调优 + 异步解析)可提升到 200-500 并发。生产级方案是 agent-go 多副本 + Milvus 向量集群 + Kafka 异步 PDF 解析,可支持 1万+ 并发。

### Q: 遇到过什么技术挑战?
> 部署时发现 doc-service 扫描 PDF 期间用户无法注册,根因是 MySQL 连接池被占满。通过分析 doc-service 连接池配置(maxconnections=20)和 MySQL 服务器 max_connections(151),定位到是连接耗尽导致 Knovis 用户服务查询超时。解决方案是降低 doc-service 连接池上限 + 提高 MySQL max_connections。

### Q: 如果要支持万人并发怎么演进?
> 主要四方面:1) MySQL 主从集群 + 读写分离;2) agent-go 微服务多副本 + K8s 自动扩缩容;3) PDF 解析异步化(Kafka + Worker 池);4) Chroma 换成 Milvus 分布式向量数据库。同时加 Sentinel 限流保护后端。
