## 五、结论与分析

### 5.1 核心发现

**rerank(bge-reranker-v2-m3)在当前配置下未带来指标提升,反而轻微下降:**

| 指标 | 变化 | 幅度 |
|------|------|------|
| Recall@5 | 88.4% → 78.5% | **-9.9%** ↓ |
| MRR | 0.8 → 0.7 | **-0.1** ↓ |
| Recall@20 | 96.0% → 96.0% | 持平 |
| 拒答率 | 40.0% → 40.0% | 持平 |
| 平均耗时 | 371.6ms → 685.0ms | **+313.4ms** ↑ |

**Recall@20 和拒答率不变是预期的**:rerank 只改变 top-20 内部的排序,不改变哪些文档进入 top-20,
也不影响基于 cosine 阈值的拒答判断(拒答用融合前 rag_raw_score)。

### 5.2 原因分析

1. **chunk 截断问题**:rerank 模型 max_length=512,但 RAG chunk 大小=800 字。
   超出 512 token 的部分被截断,导致 chunk 末尾的关键信息(如财务数据)丢失,rerank 分不准。

2. **chunk 级 vs 文档级匹配**:rerank 评估 query-chunk 语义相似度,但评测指标以 doc_name 为粒度。
   rerank 可能把一个语义相近但来自错误文档的 chunk 排到前面。

3. **融合排序已足够好**:混合策略(top-5 RRF + top-20 加权融合)的 MRR 已达 0.8,
   rerank 在此基础上引入噪声而非信号。

4. **多路召回场景(multi_recall)受影响最大**:Recall@5 从 60% 降至 40%,
   因为 multi_recall 的 query 是关键词短语(如"归属于上市公司股东的净利润"),
   rerank 模型对短 query 的语义匹配不如 BM25 精确匹配。

### 5.3 改进建议

1. **增大 max_length**:将 rerank 模型的 max_length 从 512 调到 1024,避免 chunk 截断。

2. **混合排序策略**:用 rerank 分作为加权融合分的 bonus,而非完全替换排序:
   `final_score = 0.5 * fusion_score + 0.5 * rerank_score`(而非纯 rerank 排序)。

3. **仅对 top-10 rerank**:rerank 只精排 top-10(而非全部 top-20),减少噪声干扰。

4. **分段 rerank**:对段落召回后的完整 section 文本做 rerank,而非对 chunk 做 rerank。

5. **场景路由**:multi_recall 等短 query 场景跳过 rerank,仅对 single_doc/cross_doc 启用。

### 5.4 简历可引用的量化数据

```
RAG 检索系统:BM25 + 向量混合检索(top-20)→ 段落级上下文召回 → [可选] bge-reranker-v2-m3 rerank(top-5)
基线(无 rerank):Recall@5=88.4%, Recall@20=96.0%, MRR=0.8, P95=478ms
rerank 后:Recall@5=78.5%, Recall@20=96.0%, MRR=0.7, P95=822ms
发现:rerank 在 chunk 截断(max_length=512 < chunk_size=800)下反而降低精度,
提出混合排序策略(final_score=0.5*fusion+0.5*rerank)作为改进方向。
```

### 5.5 工程启示

- **rerank 不是银弹**:在融合排序已经足够好的场景下,rerank 可能引入噪声而非信号。
  必须 before/after 量化评测,而非盲目接入。

- **截断是隐形杀手**:rerank 模型的 max_length 必须 ≥ chunk_size,否则丢失关键信息。
  这是工程实践中容易忽略的配置问题。

- **评测驱动决策**:通过 64 条 6 类场景的评测集,定位到 rerank 在 multi_recall 场景
  (Recall@5 60%→40%)和 single_doc 场景(Recall@5 100%→95%)的退化,
  为后续优化(混合排序/场景路由)提供了明确方向。
